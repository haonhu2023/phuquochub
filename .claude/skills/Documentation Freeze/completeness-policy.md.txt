# Documentation Completeness Policy

Version: 1.0.0  
Status: Production  
Owner: Chief Documentation Architect  
Priority: Critical  
Execution Mode: Read-only  
Applies To: Documentation Freeze, SSOT validation, pre-code-generation readiness

---

## 1. Purpose

This document defines the official completeness evaluation policy for all
documentation reviewed by the Documentation Freeze skill.

Its purpose is to determine whether each authoritative document contains enough
precise, actionable, and internally complete information to support
deterministic implementation.

A document is not complete merely because:

- the file exists;
- it contains many pages;
- it has professional formatting;
- it lists intended topics;
- it includes diagrams;
- it contains examples;
- it uses enterprise terminology.

A document is complete only when it fully performs its declared responsibility.

---

## 2. Core Principle

Existence is not completeness.

Length is not completeness.

Structure is not completeness.

A complete document must remove implementation-significant ambiguity.

If Claude Code must guess how to implement a documented subject, the document is
not complete.

---

## 3. Objectives

This policy must identify:

- missing required documents;
- incomplete authoritative documents;
- incomplete sections;
- empty sections;
- outline-only content;
- placeholder-only content;
- unresolved decisions;
- insufficient implementation detail;
- missing contracts;
- missing ownership;
- missing lifecycle metadata;
- missing cross-references;
- documents that appear complete but cannot support code generation.

---

## 4. Execution Mode

Completeness evaluation is strictly read-only.

Claude Code may:

- read documents;
- inspect headings;
- inspect tables;
- inspect diagrams;
- inspect examples;
- inspect cross-references;
- compare document responsibilities with actual content;
- determine required sections;
- classify completeness;
- generate findings.

Claude Code must not:

- write missing sections;
- complete the document;
- propose a hidden design;
- convert assumptions into requirements;
- change document status;
- create missing contracts;
- infer undocumented decisions;
- mark a document complete based on intent alone.

---

## 5. Completeness States

Every reviewed document must receive exactly one completeness state:

- `COMPLETE`
- `COMPLETE WITH NON-BLOCKING GAPS`
- `PARTIAL`
- `OUTLINE ONLY`
- `PLACEHOLDER ONLY`
- `EMPTY`
- `NOT FOUND`
- `NOT APPLICABLE`
- `NOT VERIFIED`

### COMPLETE

The document fully satisfies its declared purpose and supports deterministic use.

### COMPLETE WITH NON-BLOCKING GAPS

The document satisfies its authoritative purpose, but contains minor editorial,
example, or supporting gaps that do not require implementation decisions.

### PARTIAL

The document contains meaningful content but lacks one or more required
implementation-significant sections or decisions.

### OUTLINE ONLY

The document mostly contains headings, bullet lists, or topic names without
usable definitions or contracts.

### PLACEHOLDER ONLY

The document largely defers content through placeholders, promises, or open
questions.

### EMPTY

The file contains no meaningful content.

### NOT FOUND

The required artifact does not exist.

### NOT APPLICABLE

The document type is demonstrably outside the approved scope.

### NOT VERIFIED

The document exists but could not be evaluated with available evidence or tools.

`NOT VERIFIED` is never equivalent to `COMPLETE`.

---

## 6. Completeness Dimensions

Every authoritative document must be evaluated across the following dimensions.

### 6.1 Purpose completeness

The document clearly states:

- why it exists;
- what problem it governs;
- what is included;
- what is excluded;
- who uses it.

### 6.2 Scope completeness

The document defines:

- affected modules;
- affected domains;
- lifecycle scope;
- technical scope;
- exclusions;
- dependencies.

### 6.3 Definition completeness

All important concepts are defined.

No implementation-significant term remains ambiguous.

### 6.4 Contract completeness

The document specifies exact behavior, structure, or constraints where required.

### 6.5 Decision completeness

The document records final decisions rather than unresolved alternatives.

### 6.6 Dependency completeness

The document identifies required upstream and downstream dependencies.

### 6.7 Validation completeness

The document defines how compliance or success can be verified.

### 6.8 Traceability completeness

The document references related authoritative artifacts.

### 6.9 Metadata completeness

The document includes the metadata needed for governance.

### 6.10 Lifecycle completeness

The document status, approval, version, and supersession state are clear.

## 7. Metadata Requirements

Authoritative documents should contain, where governance requires:

- title;
- document ID;
- version;
- status;
- owner;
- approval authority;
- approval date;
- last updated date;
- review date;
- applies-to scope;
- classification;

Missing metadata becomes blocking when it prevents:

- authority determination;
- lifecycle determination;
- version-baseline creation;
- ownership determination;
- approval verification;
- supersession validation.

---

## 8. Structural Completeness

A document must have a structure appropriate to its purpose.

Typical required sections include:

- Purpose
- Scope
- Definitions
- Principles
- Rules or Contract
- Dependencies
- Validation
- Failure Conditions
- Evidence
- References
- Success Criteria

Not every document requires all sections.

Required structure must be derived from the document type.

---

## 9. Content Quality Threshold

Content is sufficient only when it is:

- specific;
- actionable;
- testable;
- internally consistent;
- implementation-relevant;
- free from unresolved alternatives;
- free from hidden dependencies;
- precise enough to generate acceptance criteria.

Content such as the following is insufficient:

- “Use best practices.”
- “Ensure security.”
- “Optimize performance.”
- “Support scalability.”
- “Add indexes where needed.”
- “Use appropriate permissions.”
- “Implement later.”
- “Handle errors properly.”

Such statements may express intent but do not define a contract.

## 12. ADR Completeness

An ADR is complete only when it contains:

- unique ID;
- title;
- status;
- date;
- context;
- problem;
- decision;
- alternatives considered;
- consequences;
- affected domains;
- related ADRs;
- supersession information;
- approval or acceptance evidence.

The following are incomplete:

- ADR with only a title;
- ADR with alternatives but no decision;
- ADR marked Accepted without consequences;
- ADR with no affected components;
- ADR whose status conflicts with the Decision Register.

## 36. Semantic Completeness Checks

Claude Code must not rely only on headings or keyword presence.

Evaluate whether the content answers implementation questions.

Examples:

### Weak

```text
Media may belong to different objects.
```

### Complete

```text
A media record must reference exactly one of:
place_id, event_id, review_id, post_id, wiki_revision_id.
The database enforces the exclusive arc using a CHECK constraint.
```

### Weak

```text
Use RBAC for access.
```

### Complete

```text
The endpoint requires Place.Update:Managed.
Authorization uses deny-by-default.
Explicit deny overrides inherited allow.
```

## 37. Completeness Scoring

Completeness may be scored from 0 to 100 for each document.

Recommended model:

| Dimension | Weight |
|---|---:|
| Purpose and scope | 10 |
| Definitions | 10 |
| Contract detail | 25 |
| Decisions resolved | 15 |
| Dependencies | 10 |
| Validation criteria | 10 |
| Traceability | 10 |
| Metadata and lifecycle | 10 |
| **Total** | **100** |

Suggested interpretation:

- 90–100: Complete
- 75–89: Complete with non-blocking gaps
- 50–74: Partial
- 20–49: Outline only
- 1–19: Placeholder only
- 0: Empty or not found

The score is informative.

Any implementation-significant unresolved item may still block freeze regardless
of score.

## 38. Blocking Completeness Gaps

A completeness gap blocks freeze when it leaves any of the following undefined:

- architecture choice;
- module boundary;
- technology choice;
- authoritative entity;
- field type;
- relationship ownership;
- FK;
- enum;
- discriminator;
- API path;
- request schema;
- response schema;
- auth requirement;
- permission;
- workflow transition;
- security behavior;
- migration behavior;
- acceptance criteria.

---

## 39. Non-Blocking Completeness Gaps

Examples may include:

- missing optional example;
- missing diagram caption;
- editorial wording;
- missing non-authoritative screenshot;
- minor metadata field that does not affect authority;
- absent future roadmap detail outside frozen scope.

Every non-blocking gap must still be reported.

## 43. Required Fix Guidance

Required fixes must be minimal and non-prescriptive.

### Good

```text
Define the exact discriminator values and casing for media ownership.
```

### Bad

```text
Use lowercase values place, event, review, post, wiki_revision.
```

The second statement invents the design unless already supported by evidence.

---

## 44. Interaction With Placeholder Detection

`placeholder-detection.md` identifies explicit and semantic placeholders.

This policy determines whether those placeholders make the document incomplete.

A placeholder may exist in:

- historical notes;
- rejected alternatives;
- future non-scope sections;
- templates.

Context must be considered.

---

## 45. Interaction With Consistency Validation

A document may be individually complete but inconsistent with another document.

Completeness and consistency are separate gates.

Examples:

- database document fully defines a field as `status`;
- Data Dictionary fully defines the same field as `state`.

Both documents may be complete, but the system is inconsistent.

---

## 46. Interaction With SSOT Validation

A document may be complete but not authoritative.

A document may be authoritative but incomplete.

Both conditions must be evaluated independently.

Freeze requires an authoritative and complete source for every required domain.

---

## 47. Completeness Decision

At the end of the completeness phase, issue exactly one:

- `COMPLETENESS PASS`
- `COMPLETENESS PASS WITH NON-BLOCKING GAPS`
- `COMPLETENESS FAIL`
- `COMPLETENESS BLOCKED`

This is not the final Documentation Freeze decision.

---

## 48. Completeness Pass Criteria

Issue `COMPLETENESS PASS` only when:

- every required document exists;
- every authoritative document is complete;
- no blocking section is missing;
- no implementation-significant ambiguity remains;
- metadata is sufficient for freeze governance;
- validation criteria can be derived.

---

## 49. Completeness Pass With Non-Blocking Gaps

Use only when:

- all authoritative contracts are complete;
- remaining gaps are editorial or supporting;
- no code-generation guess is required;
- gaps are explicitly recorded.

---

## 50. Completeness Fail Criteria

Issue `COMPLETENESS FAIL` when:

- one or more required documents are partial;
- blocking sections are missing;
- contract detail is insufficient;
- implementation decisions remain unresolved;
- code generation would require guessing.

---

## 51. Completeness Blocked Criteria

Issue `COMPLETENESS BLOCKED` when:

- required documents cannot be accessed;
- the scope is unknown;
- authority cannot be established;
- file formats cannot be inspected;
- a dependency prevents evaluation;
- evidence is unavailable.

## 53. Evidence Requirements

Every completeness judgment must cite:

- exact document path;
- section;
- missing section;
- heading;
- table;
- schema;
- key;
- unique text.

Do not write:

```text
The document is incomplete.
```

Write:

```text
docs/data/database.md — Media section defines ownership branches but does not
define FK ownership or cascade rules.
```

---

## 54. Self-Verification

Before publishing:

- verify all authoritative documents were evaluated;
- verify no document was marked complete based only on file existence;
- verify semantic completeness was checked;
- verify every score has a reason;
- verify every blocker identifies missing information;
- verify no missing design was invented;
- verify non-blocking gaps do not require code-generation decisions;
- verify limitations are disclosed;
- verify exactly one completeness decision is present;
- verify no files were modified.

---

## 55. Success Criteria

This policy succeeds when the Documentation Freeze audit can distinguish between:

- a document that exists;
- a document that looks complete;
- a document that is structurally complete;
- a document that is contractually complete;
- a document that is sufficiently precise for deterministic implementation.

The ultimate standard is:

> Every authoritative document contains enough exact information for Claude Code
> to implement, test, and review the approved scope without inventing missing
> behavior or making architectural decisions.
