# Purpose

This document defines

the official Authority Policy

for the PhuQuocHub platform.

The Authority Policy determines

which document

or artifact

is authoritative

when multiple sources

describe

the same topic.

Every architectural decision,

review,

implementation,

and validation

must follow

this policy.

---

# Mission

Guarantee

one authoritative source

for every subject.

Prevent

documentation conflicts.

Prevent

implementation conflicts.

Prevent

multiple truths.

Ensure

every decision

is deterministic.

---

# Fundamental Rule

For every topic

there shall be

exactly one

authoritative source.

If

multiple documents

claim authority

over the same topic,

a documentation conflict

exists.

Documentation conflicts

must be resolved

before implementation.

---

# Authority Levels

Authority is hierarchical.

Higher authority

always overrides

lower authority.

The hierarchy

must never

be violated.

---

---

# Architecture

Architecture

defines

system boundaries,

major components,

ownership,

responsibilities,

and overall design.

Nothing

may contradict

Architecture.

Architecture

is

the highest authority.

---

# Architecture Decision Records

ADRs

explain

why

architecture decisions

were made.

ADRs

must remain

consistent

with Architecture.

When

Architecture changes,

new ADRs

must be created.

Old ADRs

must never

be rewritten.

---

# Decision Register

The Decision Register

records

approved decisions

that affect

implementation.

Decision Register

must comply

with Architecture

and ADRs.

---

# Database Documentation

Database Documentation

defines

tables,

columns,

indexes,

constraints,

relationships,

and migrations.

Entities

must comply

with Database Documentation.

---

# OpenAPI

OpenAPI

defines

public API contracts.

Controllers

must implement

OpenAPI.

OpenAPI

must never

be generated

from implementation

without review.

---

# Workflow Documentation

Workflow Documentation

defines

business processes.

Implementation

must follow

Workflow.

Business logic

must never

change Workflow

without approval.

---

# Coding Standards

Coding Standards

define

style,

structure,

patterns,

naming,

layering,

and conventions.

Implementation

must comply.

---

# Repository Standards

Repository Standards

define

folder structure,

module organization,

package ownership,

and dependency rules.

Implementation

must comply.

---

# Implementation

Implementation

is

never

authoritative.

Implementation

exists

to realize

documentation.

Implementation

cannot

justify

documentation changes.

---

# Generated Files

Generated files

have

no authority.

Examples

Swagger generation

ORM generation

Client SDK generation

Compiled artifacts

Generated files

must never

be treated

as

documentation.

---

# Conflict Resolution

Whenever

two sources

conflict,

Claude Code

must

compare

their authority level.

Higher authority

wins.

Lower authority

must be updated.

---

Documentation status

are never

authoritative

Comments

Temporary notes

Personal opinions

Future plans

Unapproved drafts

Generated code

Repository state

---

# Missing Authority

no authoritative source

exists,

Claude Code

must return

NOT FOUND

No assumptions

may be made.
