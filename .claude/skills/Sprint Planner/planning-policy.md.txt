# Sprint Planning Policy

Version: 1.0

Status:
Production

Owner:
Chief Software Architect

---

# Purpose

This document defines the mandatory planning policy
for every software sprint.

Every Sprint Plan generated by Sprint Planner
MUST follow these rules.

These policies are mandatory.

They cannot be overridden unless an ADR explicitly supersedes them.

---

# Core Principle

Planning exists to reduce uncertainty.

Planning never exists to maximize code generation.

Correct planning is always preferred over fast implementation.

Architecture stability is more important than implementation speed.

---

# Planning Objectives

Sprint planning must ensure:

- predictable delivery

- architecture stability

- low integration risk

- minimal merge conflicts

- independent review

- measurable progress

- production readiness

---

Priority 1

↓

↓

Priority 5

Database

↓

Priority 6

↓

Priority 7

↓

Priority 8

Repository Status

↓

Priority 9

↓

Priority 10

Implementation

# Scope Rules

A sprint must have one objective.

Bad

Sprint

Authentication

Search

Media

Deployment

Good

Sprint

Authentication only

---

Good

Sprint

Places only

---

Good

Sprint

Wiki only

---

Good

Sprint

Production only

---

# Cohesion Rule

Modules inside one sprint
must have strong cohesion.

Example

Hotel

Restaurant

Tour

Event

can belong to one sprint.

Reason

They depend on Place Extension.

---

Bad

Authentication

Search

Production

Reason

No cohesion.

---

# Dependency Rule

A sprint
may only include modules
whose dependencies
already exist.

Example

Wiki

depends on

Places

Therefore

Wiki

cannot be scheduled

before

Places.

---

# Frozen Architecture Rule

A sprint

cannot

change architecture.

Architecture changes

require ADR.

---

# Frozen Database Rule

Database schema

cannot change

without ADR.

---

# Frozen API Rule

API contract

cannot change

without ADR.

---

# Frozen Workflow Rule

Workflow

cannot change

without ADR.

---

# Frozen RBAC Rule

Permission model

cannot change

without ADR.

---

# Frozen OpenAPI Rule

OpenAPI

is authoritative.

Implementation follows OpenAPI.

Never the reverse.

---

# Single Responsibility Sprint

Every sprint

should solve

one business capability.

Examples

Authentication

Places

Reviews

Search

Media

Analytics

Deployment

---

# Technical Debt Policy

Technical debt

shall not grow

without explicit approval.

Every sprint

must reduce

or keep debt stable.

Never increase debt silently.

---

# Risk Budget

Maximum

1 Critical Risk

or

3 High Risks

per sprint.

Otherwise

split sprint.

---

# Batch Budget

Every sprint

should contain

3–8 batches.

Maximum

12 batches.

---

# Sprint Size

Recommended

1–2 weeks

Maximum

3 weeks.

Longer sprints

increase uncertainty.

---

# Planning Constraints

The planner

must not

optimize

for

Lines of Code.

The planner

must optimize

for

architecture stability.

---

# Evidence Policy

Every planning decision

must reference

repository evidence.

Never plan

based on assumptions.

---

# Unknown Policy

If documentation

does not define behavior

Planner must report

NOT FOUND

Planner must never invent.

---

# Documentation Policy

Planning

must not

modify

documentation.

---

# Parallel Work Policy

Independent batches

may execute

in parallel.

Dependent batches

must execute

sequentially.

---

# Merge Policy

A sprint

cannot merge

unless

all batches PASS.

---

# Acceptance Policy

A sprint

cannot be accepted

unless

Architecture PASS

Security PASS

Testing PASS

Documentation PASS

Production Gate PASS

---

# Production Rule

No sprint

may deploy

directly

to production.

Every sprint

must pass

Staging

before Production.

---

# Failure Policy

If any blocker exists

Planning stops.

Planner reports

READY AFTER FIXES.

Planning never ignores blockers.

---

# Success Definition

Sprint Planning succeeds

only when

Claude Code

can implement

every batch

without making

architectural decisions.

If Claude must invent

architecture,

planning has failed.
