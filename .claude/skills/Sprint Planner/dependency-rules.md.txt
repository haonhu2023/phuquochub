# Dependency Rules

Version: 1.0

Status:
Production

Owner:
Chief Software Architect

---

# Purpose

This document defines the mandatory dependency analysis
rules used by Sprint Planner.

Dependency analysis determines

- implementation order

- sprint order

- batch order

- merge order

- deployment order

Claude Code must never generate code
without validating dependencies first.

---

# Core Principle

Dependencies define implementation order.

Implementation order never defines dependencies.

The planner must always follow the dependency graph.

Never violate dependency order.

---

# Dependency Types

Dependencies are classified into the following categories.

## Hard Dependency

A component cannot exist without another component.

Examples

Authentication

↓

Users

↓

RBAC

↓

Permissions

Without Users

Authentication cannot function.

---

## Soft Dependency

A component can operate independently,
but functionality improves if another component exists.

Example

Analytics

↓

Notifications

Analytics can exist without Notifications.

Notifications can later consume Analytics events.

---

## Optional Dependency

A feature may integrate later.

Example

AI Summary

↓

LLM Provider

The application can work without AI.

---

## External Dependency

Dependencies outside the repository.

Examples

PostgreSQL

Redis

MinIO

SMTP

Cloudflare

OpenStreetMap

Google Maps

GitHub Actions

Docker

---

## Runtime Dependency

Required only during execution.

Examples

Redis

RabbitMQ

SMTP

---

## Build Dependency

Required only during build.

Examples

TypeScript

Nest CLI

ESLint

OpenAPI Generator

---

# Dependency Principles

The planner must always prefer

low coupling

high cohesion

clear ownership

stable interfaces

minimal dependency depth

---

# Allowed Dependency Direction

Dependency direction must always move downward.

Example

API

↓

Application

↓

Domain

↓

Infrastructure

Never reverse this direction.

---

# Forbidden Dependencies

The following dependencies are prohibited.

Controller

↓

Controller

Repository

↓

Controller

Entity

↓

Service

Migration

↓

API

Database

↓

Frontend

Feature

↓

Feature

without documented contract

---

# Circular Dependency Policy

Circular dependencies are prohibited.

Examples

A → B → A

A → B → C → A

If detected

Planning stops.

Report

BLOCKER

↓

# Testing Dependency Rules

Unit Tests

↓

Integration Tests

↓

E2E Tests

↓

Performance Tests

Never skip earlier layers.

---

# Batch Dependency Rules

A batch may only contain
components whose dependencies
already exist.

Batch must never create
unresolved dependencies.

---

# Merge Dependency Rules

Batch merge order follows

Dependency Graph

never implementation speed.

---

# Dependency Validation

Before approving a sprint,
Sprint Planner must verify

All dependencies resolved

No circular dependency

No missing dependency

No undocumented dependency

No hidden dependency

No orphan module

---

# Blocking Conditions

Planning must stop if

Architecture dependency missing

Database dependency missing

ADR dependency missing

OpenAPI dependency missing

Circular dependency detected

Repository structure inconsistent

---

# Success Criteria

Dependency analysis succeeds only if

Claude Code can implement every batch
without inventing any dependency
or changing implementation order.

Dependency correctness is more important
than implementation speed.
