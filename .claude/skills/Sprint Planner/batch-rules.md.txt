# Batch Rules

Version: 1.0

Status:
Production

Owner:
Chief Software Architect

---

# Purpose

This document defines the mandatory rules
for decomposing a Sprint into implementation batches.

A Batch is the smallest independently
implementable, reviewable,
testable and mergeable unit of work.

Every Sprint must be divided into batches.

Claude Code must never implement an entire Sprint
in one generation.

---

# Core Principle

Small batches produce stable software.

Large batches create hidden bugs,
merge conflicts,
review failures,
and architecture drift.

Batch quality is always more important
than generation speed.

---

# Dependency Rule

A Batch

may only depend

on completed batches.

Never generate a batch

that depends on unfinished work.

Migration failure

Broken test

Security issue

ADR violation

Documentation drift

OpenAPI drift

RBAC drift

Performance regression

---

# Batch Rollback

Every Batch

must be reversible.

Rollback must

remove only

the current Batch.

Never affect

previous accepted batches.

---

# Batch Merge Policy

Merge only after

Architecture PASS

CI PASS

Security PASS

Documentation PASS

Never merge

FAILED batches.

# Success Criteria

A Batch is successful only if

Claude Code can implement it

without making any architectural decision,

without inventing undocumented behavior,

and without requiring future batches
to compile.

The Batch must be

independently testable,

independently reviewable,

and independently mergeable.
